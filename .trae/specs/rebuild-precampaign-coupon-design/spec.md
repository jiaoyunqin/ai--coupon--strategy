# 促前券档位设计历史对话与策略工作台重构 Spec

## Why

当前规格文件被误写成验收清单，缺少需求动机、产品边界、数据契约和可验证场景，无法作为后续实现与验收的唯一依据。同时，现有工作台存在三类需要统一解决的问题：

- “促前券档位设计”历史项需要恢复为独立三栏会话，并完整承载目标门禁、P0/P1、历史核销、实验竞对、3+X/4+X、预算治理和报告生成七步链路。
- 促前默认工作台需要以活动和参考促为上下文，在首屏提供候选策略与完整配置，并保留下方历史证据，避免候选、配置和证据相互脱节。
- 促中调优需要从并列摘要卡升级为纵向的“01 当前波次”和“02 下一波次”决策工作台，以差异矩阵、三套统一摘要卡、选中方案完整详情和独立多轮会话支撑实际调整。

最新 P1 问题还表明，非默认活动可能继承默认活动的 `profile.expansionRate` 或 `after`，批次缺值可能泄漏为 `undefined`，来源可能被误呈现为可点击链接或携带真实 URL。这些问题必须作为数据完整性和发布安全门禁，而不是仅作为视觉修复。

本规格只定义产品、数据和验收行为。本次规格修复仅允许修改 `spec.md`，不得提交或推送；未来代码实现和 GitHub 发布必须遵守本文的显式发布边界。

## What Changes

- 将“促前券档位设计”历史项恢复为左侧历史导航、中栏多轮对话、右侧七章 Queue/报告组成的独立三栏工作台。
- 将促前历史分析固定为七步：目标与约束、P0 大盘水位、P1 类目爆发、历史领券核销、实验钱效与竞对、3+X/4+X 候选、波次预算与治理。
- 保留细致的时间、类目、价格带、人群、渠道、面额、实验、竞对和预算下钻，以及逐章确认、追问和脱敏 Mock 报告。
- 将促前默认工作台统一为“活动与参考促 -> 候选策略 -> 完整券波次配置 -> 历史证据”的决策顺序。
- 活动选择继续使用轻量下拉；参考促由前序四次、同级别、同名历史和用户添加共同组成，并按动态 24 个月窗口管理。
- 促前候选保留 A-3+X 钱效优先、B-4+X 均衡增长、C-4+X 峰值增长，完整配置覆盖波次、券档与批次、人群与渠道、实验与巡检。
- 将促中调优重构为上下排列的两个独立全宽模块：01 当前波次在前，02 下一波次在后，禁止恢复左右并列卡片。
- 01 当前波次使用固定决策链和七行六列差异矩阵，并将“调整点 1 · 投放人群”“调整点 2 · 灵活渠道”作为可独立展开节点。
- 02 下一波次首屏同时呈现均衡补量、钱效优先、增长优先三套统一摘要卡；完整批次、窗口、人群、渠道、实验和护栏由下方选中方案详情承载，并保留三套候选的切换、追问和继续调整能力。
- 原始趋势、竞对、实验、领券核销、投放矩阵和技术详情下沉到决策模块之后，继续承担证据与数据追问作用。
- 新增 Task 34 对抗场景要求，验证多轮调整持久化、交叉下钻、约束冲突、缺数边界、非默认活动隔离和原方案恢复。
- 新增 P1 数据门禁：上下文严格绑定当前活动/年份/波次，批次缺值统一降级，来源仅为不可点击的脱敏标签，页面及会话不得携带真实业务 URL。
- 明确 GitHub 发布前置条件、允许文件范围、凭证与真实数据扫描、非强制推送和远端校验规则。

## Impact

- Affected state: 活动、年份、波次、参考促、候选、完整券配置、筛选条件、用户调整、报告章节和会话上下文。
- Affected data contracts: `campaign_profile`、`market_baseline`、`category_demand`、`coupon_funnel`、`experiment_groups`、`plan_candidates`、`mid_campaign_profile`、`conversation_state`、`source_label`。
- Expected implementation file: `/Users/bytedance/strategy2/index.html`。本次仅修复规格，不修改该文件。
- Regression surface: 促前/促中切换、历史会话、旧证据追问、键盘与 ARIA、响应式布局、控制台、网络请求、报告预览和下载。
- External operations: 所有预算、发券、活动立项、审批、配置、报告提交和发布均为脱敏 Mock 或待审批状态，不调用真实业务系统。
- Repository operations: 本次不提交、不推送；后续仅在用户明确授权且验收通过后执行受控发布。

## Analysis Approach

### 1. 上下文与优先级

所有推荐、证据、矩阵、批次、报告和会话必须由同一上下文键驱动：

`activityId + year + waveId + planId + filters + referenceCampaignIds`

规则如下：

- 活动、年份、波次或候选变化后，依赖内容必须原子刷新，不得残留上一上下文的数据。
- 当前上下文没有数据时显示“暂无数据”；业务上不适用时显示“不适用”。
- 不得从默认活动、固定数组下标、固定话术或其他候选中补齐非默认活动数据。
- 用户在独立方案会话中的调整形成会话增量状态，后续回答以“原始方案 + 已确认调整”为准。
- 与旧规则冲突时，以本规格中的促中决策链、P1 数据门禁和 Task 34 场景为准。

### 2. 促前历史对话七步分析

#### 第一步：目标、预算与约束门禁

AI 将自然语言目标拆成结构化决策条件：

- 核心目标：增量 GMV、DAC、订单量、结算率或用户渗透。
- 目标权重：增长目标与钱效目标之和为 100%。
- 硬约束：申请预算上限、日预算上限、CAC 上限、ROI 下限、人均补贴上限。
- 策略范围：活动日期、业务范围、主预算/子预算、主端/独立端和专项保量要求。
- 治理条件：策略、财务、业务、安全等角色确认，预算申请、立项、保密等级和参与范围。

首次进入只展示目标重述、已知数据、缺失数据、脱敏 Mock 声明和七步计划。目标或口径未确认前不得提前显示最终券方案。

#### 第二步：P0 活动前 15-20 天大盘水位

比较当前活动前窗口与去年同期，至少覆盖：

- GMV、DAC、客单、订单量和支付率。
- 20 天整体、周、日、工作日/周末粒度。
- GMV 同比约等于 DAC 变化、客单变化和交互项的贡献拆分。
- 异常日期、异常渠道及其样本限制。

本步骤必须回答当前自然水位高低、增长由 DAC 还是客单驱动，以及该水位对预算、券门槛和扩量目标的影响。

#### 第三步：P1 活动前窗口与历史活动期类目爆发

按一级类目和二级类目比较非活动窗口与历史活动期：

- GMV、DAC、客单、订单量和活动期放大系数。
- 类目增量 GMV、增量贡献率、DAC 拉动和客单拉动。
- 刚需扩量、高客单拉升、价格敏感、弱需求等需求类型。
- S/A/B/C 优先级、价格带和建议券档映射。

类目下钻必须引用当前活动及参考促样本，不得用固定类目结论覆盖所有活动。

#### 第四步：历史领券核销

按人群、渠道和面额三类主维度分析领取与核销漏斗，并支持类目、价格带、券角色和端口交叉下钻。每个切面至少展示：

- 发放 UV、领取 UV、核销 UV。
- 领取率、核销率、领取后核销率。
- 人均补贴、券引导 GMV、增量 GMV、ROI/增量 GMV 兑换比。
- 预算消耗占比、结算率和低效成本。

AI 必须区分四类问题：

- 低领取：入口、触达或券档适配不足。
- 高领取低核销：门槛、有效期或消费场景不匹配。
- 高核销低钱效：补贴过深或自然转化污染。
- 高钱效低规模：具备放量潜力，但需验证人群容量和库存。

#### 第五步：实验钱效与竞对压力

实验分析按券组展示人均支付 GMV、增量 GMV、人均增量、人均补贴、ROI、显著性、实验人群、渠道和券档组成。

竞对仅使用“竞对 A/B/C”脱敏别名，展示主档门槛、折扣深度、会员加码、张数、频次、变化方向和影响等级。竞对只作为外部压力信号，AI 必须结合自身类目需求、人群钱效、预算和显著性判断，不得因竞对补贴更深而直接建议跟随。

#### 第六步：3+X/4+X 候选生成

候选统一为：

1. A-3+X 钱效优先。
2. B-4+X 均衡增长。
3. C-4+X 峰值增长。

固定档位可使用 300-40、600-80、1500-180；4 档方案增加 3000-420；X 为按类目、价格带、人群、渠道、端口和时间窗口定向的弹性券。具体档位仅是当前 Mock profile 的配置，不得成为跨活动固定话术。

三套方案使用同一口径比较申请预算、预计结算预算、结算率、覆盖人数、发放/领取/核销、支付 GMV、增量 GMV、ROI、CAC、准备金、止损规则、适用条件和主要风险。

#### 第七步：波次预算、治理与报告

预算至少拆分为预热、第一波爆发、第二波持续、收官、专项子预算和风险准备金，并提供：

- 保守、基准、激进结算率。
- 预算缩减 10%。
- 类目需求超预期 15%。
- 库存、频控、互斥和护栏冲突。

治理状态覆盖团队确认、预算申请、活动立项、专项子预算、保密协议和发布门禁。最终只生成脱敏 Mock HTML 报告和待审批策略包，不执行真实提交。

每一步输出“结论、证据、机制、限制、下一步”。右侧章节状态必须在锁定、等待确认、排队、分析中、写入中、完成之间同步变化；用户确认计划后只生成 P0，后续章节由对话动作逐步解锁。

原型演示中，每章单次推进约 2.6 秒，并清晰呈现排队、分析和写入阶段。报告支持自定义标题、隐藏与恢复章节、预览、全屏和下载；隐藏章节必须可恢复，不得从报告状态中永久删除。

### 3. 促前默认工作台

促前默认工作台按以下顺序组织：

1. 轻量活动下拉与当前活动摘要。
2. 可增删的参考促集合与覆盖摘要。
3. A/B/C 候选策略摘要。
4. 完整券波次配置。
5. 历史证据、原始数据和追问入口。

参考促规则：

- 自动纳入所选活动之前最近四次已结束活动。
- 自动纳入同级别活动和同名历史活动。
- 以规划活动日期为锚点，仅自动使用向前 24 个月窗口内的数据，排除未来活动。
- 去重后保留“前序四次、同级别、同名历史、用户添加”等全部命中原因。
- 自动样本按实际日期间隔连续衰减；仅由用户添加的样本使用中立权重。
- 删除后重新加入同一自动样本时，恢复原自动原因和权重，并叠加“用户添加”来源标记。

完整配置包含：

- 波次总览：周期、主端/独立端、预算占比、目标、券档、人群和场域。
- 券档与批次：场域计划、批次计划、批次列表、投放活动列表、发放/使用窗口、限领频控。
- 人群与渠道：价值、潜力、新客、回流等分层与会场、搜索、券包、Push、内容场、独立端矩阵。
- 实验与巡检：历史实验、C/T1/T2 分流、联合护栏、基础信息、实验参数、增发追补、投放一致性和发布边界。

历史证据继续覆盖大盘水位、类目爆发、价格带、券档核销、波次、人群、竞对和来源。候选是待共创方案，不代表预算已提交、配置已生效或活动已发布。

### 4. 促中纵向决策工作台

促中必须按“01 当前波次 -> 02 下一波次 -> 下沉证据”的顺序纵向排列，两个模块均为独立全宽区域。

#### 01 当前波次

固定决策链依次为：

1. 当前上下文与异常诊断。
2. 调优目标和硬约束。
3. 七行六列差异矩阵。
4. 调整点 1 · 投放人群。
5. 调整点 2 · 灵活渠道。
6. 关键指标、风险和止损线。
7. 独立追问与基于方案继续调整。

差异矩阵六列固定为：

1. 调整对象。
2. 调整前。
3. 调整后。
4. 决策依据。
5. 预估影响。
6. 风险/止损。

差异矩阵七个决策维度固定为：

1. 目标与当前诊断。
2. 券角色与券档。
3. 投放人群。
4. 渠道与场域。
5. 端口与时间窗口。
6. 预算、库存、限领与频控。
7. 实验、指标护栏与回滚。

“投放人群”和“灵活渠道”可分别展开和收起，均使用上述六字段口径；两者状态、内容和会话上下文互不覆盖。动作支持放量、缩量、换档、迁移、催用、停投、保留对照和回滚，并细化到人群、券角色/档位、渠道/场域、端口和时间窗口。

#### 02 下一波次

首屏同时展示三套统一口径的决策摘要卡。候选保留：

- 均衡补量。
- 钱效优先。
- 增长优先。

每张摘要卡必须包含方案定位、净增预算、覆盖规模、增量 GMV、ROI、核心券档动作、人群与场域、适用条件和主要风险。三套方案使用同一指标顺序和信息结构进行比较。

推荐候选需要明确标记，非推荐候选不得折叠或隐藏。点击任一摘要卡后，下方展示该候选的完整批次、发放/使用窗口、限领频控、端口、人群、场域、实验、完整指标、来源和止损线。每张卡仅保留“基于此方案继续调整”，方案级独立追问集中在选中方案详情区。

#### 下沉证据与入口语义

趋势、KPI、归因、竞对、实验、领券核销和投放矩阵位于 01/02 之后，继续按当前筛选上下文刷新。旧证据入口保持“数据追问”语义，只有当前波次和三套下一波次方案入口可以创建方案上下文。

### 5. Task 34 对抗分析

方案会话必须通过以下对抗场景：

- 多轮调整：用户先修改人群、渠道、券档或预算，后续回答中的方案、指标、风险和冲突判断真实反映该调整。
- 三维交叉下钻：典型“人群 × 券档 × 渠道”等组合返回当前方案内一致的数值、口径和证据，不退化为固定模板。
- 细分维度下钻：券角色、行业/价格带、端口和时间窗口均保留当前活动、波次和候选上下文。
- 约束冲突：识别预算、库存、限领、频控、互斥或 ROI 护栏冲突，并给出取舍、降级或回滚边界。
- 未建模或缺数：明确显示“暂无数据”或“不适用”，不编造批次、精确指标或确定性结论。
- 非默认活动：618、双11等活动必须读取自身 profile，不命中与当前 profile 无关的固定“300-40”“高价值 X 券”话术。
- 会话稳定性：连续至少三轮调整、下钻和约束追问后仍停留在当前独立会话，并可恢复原方案。

### 6. 质量与回归方法

实现阶段至少验证：

- JavaScript 语法、静态重复 ID、敏感信息、真实业务 URL、批次 `undefined`、目标文案和 `git diff --check`。
- 默认及非默认活动、不同年份/波次、三套摘要候选、七行六列矩阵、两个独立展开点和选中方案完整详情。
- 桌面宽屏、1440px、1307px、1280px、1024px 下无横向溢出、文字截断、按钮遮挡或决策顺序错位。
- 候选切换、调整点展开/收起、追问和继续调整支持 Enter/Space，`aria-selected`、`aria-expanded` 与视觉状态同步。
- 促前历史七步门禁、促前默认工作台、促中旧证据追问和“促中预算紧张”等历史会话无新增回归。

## Mock Contract

### 1. 脱敏与安全规则

- 活动、实验、站点、人群、券池和批次 ID 使用不可逆 Mock 别名，如 `CMP_26_618_A`、`EXP_G03`、`SITE_****`、`BATCH_MOCK_02`。
- 竞对只显示“竞对 A/B/C”，团队和审批人只显示角色。
- 金额按统一比例缩放并取整，用户规模使用区间或汇总值，日期整体平移到演示周期。
- 所有数据标注“脱敏 Mock，仅用于原型演示”。
- 业务来源只保存 `sourceId`、脱敏名称和来源类型，不保存 `href`、`url`、内部域名或真实查询参数。
- 来源标签不可点击，不使用链接角色、外链图标或跳转行为，也不进入键盘链接焦点序列。
- Mock 数据不得触发真实查询、预算、发券、审批、活动配置或发布。

## ADDED Requirements

### Requirement: 促前历史对话三栏入口

系统 SHALL 在点击“促前券档位设计”时进入独立三栏工作台，而不是只显示 Toast。

#### Scenario: 进入历史会话

- **WHEN** 用户点击左侧“促前券档位设计”
- **THEN** 左侧保持历史导航和选中状态
- **AND** 中栏显示促前多轮对话与固定输入
- **AND** 右栏显示七章 Queue/报告

#### Scenario: 首次进入

- **WHEN** 用户首次进入该历史会话
- **THEN** 只显示目标重述、已知与缺失数据、脱敏 Mock 声明和七步计划
- **AND** 不提前显示最终券档、预算或推荐方案

### Requirement: 七步交互门禁

系统 SHALL 按目标约束、P0、P1、核销、实验竞对、候选、预算治理的顺序逐章推进。

#### Scenario: 确认分析计划

- **WHEN** 用户确认目标和七步计划
- **THEN** 系统只生成 P0 大盘水位
- **AND** P1 及后续章节保持锁定

#### Scenario: 推进后续章节

- **WHEN** 用户完成当前章节的确认或追问动作
- **THEN** 下一章节进入排队、分析、写入和完成状态
- **AND** 中栏对话与右栏报告状态保持一致

#### Scenario: 形成最终产物

- **WHEN** 七步分析及治理确认完成
- **THEN** 系统生成脱敏 Mock HTML 报告和待审批策略包
- **AND** 不触发真实预算、发券、审批或发布

#### Scenario: 管理报告

- **WHEN** 用户自定义标题、隐藏或恢复章节，或打开报告预览
- **THEN** 报告状态与 Queue 保持一致
- **AND** 支持全屏、返回队列和下载
- **AND** 单章推进以约 2.6 秒展示排队、分析和写入过程

### Requirement: P0/P1 与历史证据下钻

系统 SHALL 提供活动前 15-20 天大盘水位、活动期类目爆发、历史核销、实验和竞对的细致证据。

#### Scenario: 查看 P0

- **WHEN** 用户查看 P0
- **THEN** 页面展示 GMV、DAC、客单、订单量、支付率、同比和贡献拆分
- **AND** 解释自然水位对券门槛、预算和扩量目标的影响

#### Scenario: 查看 P1

- **WHEN** 用户查看 P1 并下钻类目
- **THEN** 页面展示一级到二级类目的 GMV、DAC、客单、放大系数、增量贡献、价格带和优先级
- **AND** 所有结论绑定当前活动和参考促

#### Scenario: 识别核销问题

- **WHEN** 某切面出现低领取、高领取低核销、高核销低钱效或高钱效低规模
- **THEN** AI 按对应机制解释并给出下一步验证
- **AND** 引用当前人群、渠道、面额和交叉下钻证据

#### Scenario: 解释竞对压力

- **WHEN** 竞对 Mock 显示更深补贴
- **THEN** AI 结合自身类目、人群、实验显著性和预算约束判断
- **AND** 不直接建议跟随竞对

### Requirement: 促前活动与参考促

#### Scenario: 切换活动

- **WHEN** 用户从 KPI、趋势、归因或竞对等证据入口追问
- **THEN** 保持数据追问语义
- **AND** 不创建或覆盖方案调整状态

### Requirement: 缺数与来源展示

所有工作台、报告和会话 SHALL 使用统一缺数语义和脱敏来源语义。

#### Scenario: 同一缺值跨界面出现

- **WHEN** 同一批次缺值出现在矩阵、详情、报告和会话
- **THEN** 各处使用一致的“暂无数据”或“不适用”

#### Scenario: 同一来源跨界面出现

- **WHEN** 同一来源出现在促前、促中、报告和会话
- **THEN** 各处均为不可点击的相同脱敏标签

### Requirement: 统一可访问性与报告状态

交互控件 SHALL 提供可读名称、键盘操作和同步 ARIA 状态；报告 Queue SHALL 与分析进度一致。

#### Scenario: 键盘操作

- **WHEN** 用户使用 Enter/Space 操作候选、Tab 或展开控件
- **THEN** 视觉选中/展开状态与 `aria-selected`、`aria-expanded` 同步

#### Scenario: 报告状态更新

- **WHEN** 某章节从锁定进入生成并完成
- **THEN** Queue、中栏消息和报告画布显示一致状态

## REMOVED Requirements

### Requirement: 促前历史项仅显示 Toast

**Reason**: Toast 无法承载七步分析、追问和报告。

**Migration**: 替换为独立三栏历史会话。

#### Scenario: 点击历史项

- **WHEN** 用户点击“促前券档位设计”
- **THEN** 不再以 Toast 作为最终响应

### Requirement: 促类型选择和活动卡片墙

**Reason**: 促类型可由活动元数据确定，大面积卡片墙增加无效选择和首屏负担。

**Migration**: 使用轻量活动下拉，并由系统自动计算同级别和同名历史样本。

#### Scenario: 进入促前规划

- **WHEN** 用户进入促前默认工作台
- **THEN** 不显示促类型选择步骤或活动卡片墙

### Requirement: 数据看板优先和促中左右并列卡片

**Reason**: 数据看板优先要求用户自行归纳结论，左右并列卡片无法承载完整决策链和多方案比较。

**Migration**: 促前使用候选与完整配置优先；促中使用纵向 01/02 全宽模块；原数据下沉为证据。

#### Scenario: 查看策略工作台

- **WHEN** 用户进入促前或促中
- **THEN** 不以原始图表或左右并列摘要卡作为首要决策内容

### Requirement: 默认活动兜底和固定方案话术

**Reason**: 跨活动兜底会造成错误推荐和不可追溯结论。

**Migration**: 使用完整上下文键精确读取；缺数时显式降级。

#### Scenario: 非默认活动缺数

- **WHEN** 非默认活动缺少 profile 或某维度
- **THEN** 不继承默认活动，不使用固定券档话术

### Requirement: 批次 `undefined` 与伪造精确值

**Reason**: 技术缺值泄漏和伪造值都会误导策略判断。

**Migration**: 统一映射为“暂无数据”或“不适用”。

#### Scenario: 序列化缺失批次

- **WHEN** 页面生成详情、报告或会话上下文
- **THEN** 输出中不存在 `undefined` 或虚构批次值

### Requirement: 可点击业务来源和真实业务 URL

**Reason**: 原型不应暴露内部资源位置，也不应让脱敏来源呈现真实跳转能力。

**Migration**: 只保留不可点击的脱敏来源标签。

#### Scenario: 查看或操作来源

- **WHEN** 用户点击或键盘操作来源标签
- **THEN** 不发生导航
- **AND** 页面及上下文中不存在真实业务 URL

### Requirement: 自动执行真实操作或未授权发布

**Reason**: 原型与策略共创不具备真实发券、预算、审批、配置或仓库发布授权。

**Migration**: 业务动作保持 Mock/待审批；GitHub 发布仅在用户明确授权和全部验收通过后执行。

#### Scenario: 确认方案但未授权发布

- **WHEN** 用户确认候选或完成报告，但未明确授权真实操作或 GitHub 发布
- **THEN** 系统只保存 Mock/待审批状态
- **AND** 不提交、不推送、不调用真实业务系统
